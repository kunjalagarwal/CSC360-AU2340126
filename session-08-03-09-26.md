# Class Reflection(03 Sept, 26)

## Overview

Today's class focused on understanding how software can be designed to be **robust, flexible, and user-friendly**, especially in situations where traditional graphical interfaces may not be available. We explored concepts such as ASCII-based representations, headless applications, testing, object-oriented design, job management, and graceful process termination.

## ASCII Tree and Text-Based Representation

One of the concepts discussed was how to **print an ASCII tree** instead of drawing a tree graphically. Using text to represent structures can be more robust because it does not depend on a graphical interface or a monitor. Even in a **headless environment**, where there is no graphical display available, users can still read and understand the output through a terminal.

This made me understand that graphical representation is not always necessary. For certain applications, especially command-line tools and server environments, a well-formatted text representation can be more practical and reliable.

## Headless Applications

We also discussed the concept of **headless systems**. A headless application operates without a graphical user interface or monitor. This is common in servers, cloud environments, and automated systems.

The discussion helped me understand why applications should not always depend on a GUI. Designing software that can work through the command line or other non-graphical interfaces makes it more flexible and suitable for different environments.

## Drawing Arrows Between Lists

Another interesting problem was **drawing arrows between two lists when they contain common elements**. The idea is to identify matching elements between the lists and visually represent their relationships using arrows.

This problem demonstrates how data can be represented not only as individual values but also through the **relationships between objects or collections**. It is useful for understanding mappings and connections between different data structures.

## Unit Testing vs Acceptance Testing

We discussed the difference between **unit tests and acceptance tests**.

* **Unit testing** focuses on testing a small, individual component of a program, such as a function or class, in isolation.
* **Acceptance testing** checks whether the complete system behaves according to the requirements from a user's or customer's perspective.

This distinction helped me understand that testing happens at different levels. A program can have correctly working individual components but still fail to satisfy the overall requirements.

## Custom Splash Screen Using FXML

We also explored how to create a **custom splash screen using FXML**. This demonstrated how the user interface can be separated from the application logic.

Using FXML allows the structure and appearance of the interface to be defined separately from the Java code. This makes the application easier to organize, maintain, and modify.

## Tree of Objects with Editing Support

Another concept was creating a **tree of objects where each object can be edited**. This is useful when dealing with hierarchical data, where objects have parent-child relationships.

The important part was not just displaying the tree but also allowing users to modify individual objects. This introduced the idea that a data structure can also serve as an interactive interface for managing and editing objects.

## Composite Progress Bar for Multiple Jobs

We discussed a **composite progress bar** that can track multiple jobs and support cancellation. Instead of having one progress indicator for the entire application, different tasks can be tracked together while still maintaining information about their individual progress.

The cancellation feature is particularly important because users should be able to stop a task when it is no longer required. This introduced the idea of designing long-running operations with proper control and feedback.

## Operating System Process Management

A major concept discussed was how operating systems manage processes, similar to how applications such as **Chrome** manage multiple tasks or processes.

We learned that stopping a process should not necessarily mean forcefully terminating it. Instead, the system can **send a signal requesting the process to stop**. The process can then perform necessary cleanup and terminate gracefully.

This is an important concept because forcefully stopping a process can leave resources in an inconsistent state. Graceful termination allows the application to close files, release resources, finish necessary operations, and shut down properly.

## Key Takeaways

The main things I learned from this class were:

1. **Text-based representations can be more robust than graphical representations**, especially in headless environments.
2. **Headless applications** are useful when a graphical interface is unavailable or unnecessary.
3. Relationships between data structures can be represented visually using concepts such as **arrows and mappings**.
4. **Unit tests and acceptance tests serve different purposes** and operate at different levels of software testing.
5. **FXML** can help separate UI design from application logic.
6. Hierarchical data can be represented using an **editable object tree**.
7. Long-running tasks should provide **progress tracking and cancellation support**.
8. Operating systems and applications should prefer **graceful process termination** over forceful stopping.
9. Sending a signal to stop a process gives it an opportunity to **clean up resources and terminate safely**.
